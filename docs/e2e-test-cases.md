# E2E-тест-кейсы Unitman Front

Документ описывает сквозные (end-to-end) проверки интерфейса `unitman-front`.
Тесты автоматизируют пользовательские сценарии в реальном браузере, но
**бэкенд заменяется детерминированными моками HTTP API** (Playwright
`page.route`). Это даёт быстрые и стабильные проверки UI без запуска
PostgreSQL, Temporal, RoadRunner и Centrifugo.

## 1. Область и принципы

### Что проверяем

- маршрутизацию и guard'ы (авторизация, роли, 404);
- вход/выход и восстановление сессии;
- отрисовку списков, пустых состояний и ошибок загрузки;
- клиентскую фильтрацию и синхронизацию фильтров с URL;
- отправку команд на бэкенд (проверяется форма запроса, а не ответ БД);
- состояния загрузки/ошибки/успеха в формах;
- навигацию по сайдбару и шапке, смену темы и языка.

### Что не проверяем в этом контуре

- реальные сборки юнитов, Docker, раннеры и Temporal;
- WebSocket-доставку (Centrifugo) — сокет маршрутизируется в no-op;
- Web Push, Service Worker и реальные браузерные разрешения;
- визуальную регрессию (скриншотные эталоны);
- нагрузочные и security-тесты;
- контракт бэкенда — для него есть PHPUnit (`unitman/`).

### Инструменты и соглашения

| Параметр | Значение |
| --- | --- |
| Фреймворк | `@playwright/test` |
| Браузер | Chromium (Desktop Chrome) |
| Язык UI по умолчанию | `ru` |
| Базовый URL | `http://127.0.0.1:5173` (Vite dev server) |
| API | `VITE_API_HOST=/api`, все запросы перехватываются моками |
| Авторизация | подмена `localStorage.tokenData` валидным JWT |
| Селекторы | ARIA-роли, `getByLabel`, видимый текст, стабильные `id` полей |

Все моки API описаны в `e2e/support/`. Ответы бэкенда оборачиваются в конверт
`{status: "success", data: ...}`; ошибки — `{status: "fail", data: {message}}`.
Неизвестный запрос получает `fail`, поэтому «лишний» сетевой вызов виден в
отчёте, а не маскируется пустым ответом.

### Тестовые данные

Базовые сущности создаются фабриками (`e2e/support/data.ts`):

- **Администратор**: `admin@e2e.local`, роли `ROLE_ADMIN`, `ROLE_USER`.
- **Пользователь**: `user@e2e.local`, роль `ROLE_USER`.
- **Юнит**: `feature/e2e-1` проекта `e2e-project`.
- **Проект**: `e2e-project` / `E2E Project`.
- **Репозиторий**: `e2e-repo` типа `gitlab`.
- **Раннер**: `runner-e2e-1` со снимком ресурсов.

Фильтры и настройки интерфейса в `localStorage` сбрасываются перед каждым
тестом, чтобы предыдущий сценарий не влиял на следующий.

## 3. Детальные сценарии

Ниже — шаги и ожидаемые результаты для автоматизированных кейсов. Названия
спеков указаны относительно `unitman-front/e2e/tests/`.

### E2E-AUTH-01 — Редирект на страницу входа

- **Предусловия:** сессия отсутствует.
- **Шаги:**
  1. Открыть `/unit/list`.
- **Ожидаемый результат:** URL содержит `/login`; отображается форма входа;
  в `localStorage` нет `tokenData`.
- **Автотест:** `auth.spec.ts` → «перенаправляет неавторизованного на /login».

### E2E-AUTH-02 — Форма входа

- **Предусловия:** сессия отсутствует.
- **Шаги:**
  1. Открыть `/login`.
- **Ожидаемый результат:** видны поля `Email` и `Пароль`, кнопка `Вход`.
- **Автотест:** `auth.spec.ts` → «показывает форму входа».

### E2E-AUTH-03 — Ошибка входа

- **Предусловия:** сессия отсутствует; `POST /login` отвечает `fail`.
- **Шаги:**
  1. Открыть `/login`.
  2. Ввести `admin@e2e.local` / `wrong`.
  3. Нажать «Вход».
- **Ожидаемый результат:** появляется баннер «Ошибка входа» с текстом мока;
  маршрут остаётся `/login`, `tokenData` не сохранён.
- **Автотест:** `auth.spec.ts` → «показывает ошибку при неудачном входе».

### E2E-AUTH-04 — Успешный вход

- **Предусловия:** сессия отсутствует; `POST /login` отвечает успехом с JWT.
- **Шаги:**
  1. Открыть `/login`.
  2. Ввести валидные данные.
  3. Нажать «Вход».
- **Ожидаемый результат:** переход на `/unit/list`; в `localStorage.tokenData`
  лежит токен; в шапке виден email пользователя.
- **Автотест:** `auth.spec.ts` → «успешный вход сохраняет сессию и ведёт в юниты».

### E2E-AUTH-05 — Возврат на исходный URL

- **Предусловия:** сессия отсутствует; открыт защищённый `/unit/projects`.
- **Шаги:**
  1. Дождаться редиректа на `/login`.
  2. Войти.
- **Ожидаемый результат:** после входа открыт `/unit/projects`, а не
  `/unit/list`.
- **Автотест:** `auth.spec.ts` → «возвращает на исходный защищённый URL».

### E2E-AUTH-06 — Повторный вход

- **Предусловия:** валидная сессия администратора.
- **Шаги:**
  1. Открыть `/login`.
- **Ожидаемый результат:** показывается «Уже авторизован» и кнопка «Выйти»;
  форма логина скрыта.
- **Автотест:** `auth.spec.ts` → «показывает состояние уже авторизованного».

### E2E-AUTH-07 — Выход

- **Предусловия:** валидная сессия администратора, открыт `/login`.
- **Шаги:**
  1. Нажать «Выйти».
- **Ожидаемый результат:** `localStorage.tokenData` удалён, форма входа снова
  доступна, маршрут `/login`.
- **Автотест:** `auth.spec.ts` → «выход очищает сессию».

### E2E-NAV-01/02/03 — Сайдбар и роли

- **Предусловия:** сессия администратора или пользователя.
- **Шаги:**
  1. Открыть `/unit/list`.
- **Ожидаемый результат:**
  - у администратора видны «Главная», «Юниты», «ИИ-помощник», «Настройки» и
    группа «Администрирование» с «Аккаунты», «Репозитории», «Проекты», «Раннеры»;
  - у обычного пользователя группа «Администрирование» и её пункты отсутствуют.
- **Автотесты:** `navigation.spec.ts` → «показывает основную навигацию»,
  «администратор видит раздел администрирования»,
  «пользователь не видит раздел администрирования».

## 4. Запуск

```bash
cd unitman-front
yarn install
yarn playwright install chromium
yarn test:e2e            # headless
yarn test:e2e:ui         # интерактивный UI-режим
yarn test:e2e:report     # открыть HTML-отчёт
```

Если на хосте нет системных библиотек Chromium (`libasound2` и др.) и нет
прав на `playwright install-deps`, тесты можно запустить в официальном образе
Playwright той же версии:

```bash
docker run --rm --network host --ipc=host \
  -v "$PWD":/work -w /work \
  mcr.microsoft.com/playwright:v1.48.2-jammy \
  ./node_modules/.bin/playwright test \
    --config=playwright.config.cjs --workers=1
```

Конфигурация Playwright сама поднимает Vite dev server (`yarn dev`) на
`http://127.0.0.1:5173` и передаёт `VITE_API_HOST=/api`. Если сервер уже
запущен, он будет переиспользован.

По умолчанию включены 2 повтора упавших тестов. Это компенсирует
инфраструктурный `ERR_NETWORK_CHANGED`, при котором Chromium в контейнерных
окружениях иногда обрывает загрузку модулей Vite. Детерминированные ошибки
повтором не маскируются: они падают во всех трёх попытках.

Переменные:

| Переменная | Назначение |
| --- | --- |
| `E2E_BASE_URL` | внешний URL приложения; если задан, `webServer` не стартует |
| `CI` | включает повторы упавших тестов и запрет `test.only` |

## 5. Артефакты

При падении Playwright сохраняет скриншот, видео и trace:

```
unitman-front/e2e/.artifacts/
unitman-front/e2e/report/
```

Обе папки исключены из git. Для разбора падения:

```bash
yarn playwright show-trace e2e/.artifacts/<test>/trace.zip
```

## 7. Подтверждение email и OAuth

- Самостоятельная регистрация переводит на `/verify-email` с подставленным email.
- Верный 6-значный код показывает успех и сообщение об ожидании активации.
- Неверный/просроченный код показывает понятную ошибку на странице подтверждения.
- `/oauth/callback?code=...` обменивает код на токены, сохраняет сессию и ведёт
  на `/pending` или `defaultRoute` в зависимости от флагов пользователя.
- `/login?oauthError=oauth.account.blocked` показывает сообщение о блокировке.
- Пользователь без подтверждённого email после входа попадает только на
  `/verify-email`; подтверждённый, но неактивированный — на `/pending`.
